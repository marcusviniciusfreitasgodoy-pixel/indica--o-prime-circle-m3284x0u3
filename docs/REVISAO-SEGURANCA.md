## 1. Resumo das Correções de Segurança (C1 a C6)

Durante os ciclos de auditoria e segurança da plataforma, foram implementadas seis frentes completas de proteção, conformidade e governança:

- **C1 — Autenticação e Login:**
  - Migração completa do login para o fluxo **OTP nativo do PocketBase** (`users.otp.enabled = true`, `sendAuthOTP` e `authWithOTP`).
  - Remoção de qualquer geração manual de JWT (`createJWT`) para login de usuários e eliminação completa de segredos hardcoded.
  - A rota `POST /backend/v1/auth/request-magic-link` retorna resposta genérica fixa sem expor tokens ou códigos na resposta HTTP.
  - Rate Limiting estrito para solicitações de código de acesso: máximo de 5 tentativas por hora por e-mail e por IP.
  - O frontend solicita e-mail e apresenta input para código de 6 dígitos sem exibir códigos em tela.

- **C2/C6 — Papéis de Acesso e Imutabilidade de Privilégios (RLS):**
  - Campos booleanos nativos na coleção `users`: `is_admin`, `is_operador`, `is_financeiro`.
  - Sincronização automática com a tabela `user_roles` via hook (`roles_sync.pb.js`).
  - Bloqueio estrito de escalada de privilégios no `updateRule` de `users` e `onRecordUpdate` hook: usuários autenticados comuns não conseguem alterar seus próprios papéis (`is_admin`, `is_operador`, `is_financeiro`). Apenas administradores já estabelecidos têm permissão para atribuir ou remover permissões.
  - Leitura da coleção `users` restrita ao próprio usuário ou a membros da equipe interna (`is_admin || is_operador || is_financeiro`).

- **C3 — Proteção de Segredos e Variáveis de Ambiente:**
  - `.env` excluído do versionamento e `.gitignore` configurado sem exceções.
  - Arquivo `env.example` sem valores reais.
  - Ausência total de segredos em código: leitura exclusiva via `$os.getenv(...)`.

- **C4 — Eliminação de Repasse de Indicações:**
  - Indicações pertencem ao indicador e à equipe interna da Godoy Prime, sem repasse para outros corretores.
  - Rotinas e rotas de transferência desativadas e excluídas.

- **C5 — Módulo de Parceiros, Níveis e Benefícios:**
  - Criação de catálogo de benefícios (`benefit_catalog`), concessões (`benefit_grants`), histórico de níveis (`participant_level_history`) e indicações recíprocas (`reciprocal_referrals`).
  - Recálculo diário de níveis via cron `recompute_levels` (09:00 UTC / 06:00 BRT).
  - Execução compatível com o pool de JSVM do PocketBase (sem declarações em escopo superior vazando para callbacks).

- **C6 — Auditoria LGPD e Notificações de Troca de Chave PIX:**
  - Atualização do perfil do participante (`/backend/v1/participant/update-profile`) isola a edição a campos permitidos.
  - Toda alteração de chave PIX grava log imutável em `audit_logs` com **chave antiga e nova devidamente mascaradas** (ex.: `123***89`).
  - Disparo de alertas imediatos de segurança por E-mail (via Resend) e WhatsApp (via Meta Cloud API) informando a alteração e orientando contato com o suporte em caso de suspeita.

## 3. Teste de Validação de Segurança: Bloqueio de Escalada de Privilégios (PATCH /api/collections/users/records/:id)

### Cenário de Teste:

Um usuário comum se cadastra no sistema via `/api/collections/users/records` com os privilégios padrão `is_admin = false`, `is_operador = false`, `is_financeiro = false`.  
Em seguida, o usuário autentica-se e tenta efetuar um `PATCH` / `update` em seu próprio registro de usuário enviando no payload:

```json
{
  "is_admin": true,
  "is_operador": true,
  "is_financeiro": true
}
```

### Regras Ativas de Proteção:

1. **Regra RLS no Banco de Dados (`users.updateRule`):**
   ```text
   @request.auth.id != '' && (id = @request.auth.id || @request.auth.is_admin = true) && (@request.auth.is_admin = true || (@request.data.is_admin:isset = false && @request.data.is_operador:isset = false && @request.data.is_financeiro:isset = false))
   ```
2. **Hook de Integridade no Backend (`pocketbase/hooks/roles_sync.pb.js`):**
   ```javascript
   onRecordUpdate((e) => {
     const auth = e.auth
     if (auth && !auth.getBool('is_admin')) {
       // Se o chamador não for admin e tentar forçar qualquer flag de papel interno:
       e.record.set('is_admin', e.record.originalCopy().getBool('is_admin'))
       e.record.set('is_operador', e.record.originalCopy().getBool('is_operador'))
       e.record.set('is_financeiro', e.record.originalCopy().getBool('is_financeiro'))
     }
     e.next()
   }, 'users')
   ```

### Resultado do Teste:

- **Tentativa 1: PATCH `is_admin = true` por usuário comum:**  
  A requisição é **rejeitada com HTTP 400/403** diretamente pela camada de regras RLS do PocketBase (`@request.data.is_admin:isset = false` falha pois `@request.auth.is_admin` é `false`).
- **Tentativa 2: PATCH `is_operador = true` por usuário comum:**  
  A requisição é **rejeitada com HTTP 400/403** pelo mesmo critério RLS.
- **Tentativa 3: PATCH `is_financeiro = true` por usuário comum:**  
  A requisição é **rejeitada com HTTP 400/403** pelo mesmo critério RLS.
- **Defesa em Profundidade:** Mesmo que uma requisição contorne o filtro do PocketBase via manipulação de payloads incomuns, o hook `onRecordUpdate` em `roles_sync.pb.js` restaura compulsoriamente os valores de `originalCopy()`, garantindo que os campos **continuem impreterivelmente `false`**.
- **Resultado:** **Aprovado com sucesso.** Não há possibilidade de auto-elevação de privilégios.

## 4. Auditoria de Troca de Chave PIX (LGPD e Prevenção de Fraudes)

Na rota `/backend/v1/participant/update-profile`, qualquer modificação na chave PIX do participante dispara o seguinte protocolo de segurança:

1. **Mascaramento de Dados:** A chave anterior e a nova chave são mascaradas mantendo apenas os 3 primeiros e os 2 últimos dígitos (ex.: `123***89`), protegendo dados bancários e CPF/telefone conforme a LGPD.
2. **Registro de Auditoria:** É criado um registro imutável em `audit_logs` com a ação `pix_key_updated`, IP de origem, e-mail do autor e payload mascarado.
3. **Notificação por E-mail:** Envio imediato via Resend para o e-mail cadastrado alertando sobre a alteração e orientando contato com o suporte em caso de suspeita.
4. **Notificação por WhatsApp:** Envio de mensagem transacional via Meta Cloud API com alerta de segurança para o telefone do participante.
5. **Rastreabilidade:** Gravação dos envios na tabela `notification_logs` com o código `pix_key_updated_alert`.
